# ARTEX 企业版首版设计：项目、角色权限与存量迁移

**评审稿 · 2026-11-23 · 基线 `Sycun/ARTEX@6997a46`**

一个企业私有部署一套 ARTEX。一个员工可以参加多个项目，在不同项目承担不同职责。首版以**项目**作为业务数据的授权边界，以**实名人员或项目服务账号**作为操作主体。沿用现有 Go 服务、PostgreSQL 和任务 ID。文中的实体、权限和迁移步骤均为拟议设计，验收使用合成数据或脱敏历史副本。

## 一、调研结论与首版取舍

| 一手资料 | 给 ARTEX 的设计决定 |
| --- | --- |
| GitLab 允许同一用户在不同项目中承担不同角色。[项目角色](https://docs.gitlab.com/user/permissions/) | 角色授予到项目。一个项目组由这个项目的有效成员组成。首版直接维护人员名册，员工可跨项目任职。若两个部门共同交付一个项目，将两边人员加入同一名册。 |
| OWASP 建议默认拒绝、逐请求授权，同时检查主体与资源的关系，静态文件也要受保护。[授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) | 角色决定可以做哪些动作，资源归属决定对哪个项目生效。项目列表、详情、事件流、导出、下载和后台处理都使用同一组规则。 |
| OIDC 规定签发方与主体标识的组合可以稳定标识用户，邮箱可变。[OpenID Connect Core §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability) | 企业身份源负责登录，ARTEX 按 `(iss, sub)` 绑定内部用户 ID。改名或改邮箱保留授权历史。项目角色由 ARTEX 管理。 |
| PostgreSQL 16 支持先添加待验证的外键或检查约束，再验证历史数据。GitLab 的批迁移要求小批次可重试。[PostgreSQL 约束](https://www.postgresql.org/docs/16/sql-altertable.html) · [GitLab 批迁移](https://docs.gitlab.com/development/database/batched_background_migrations/) | 先扩展结构，再按对象回填，最后收紧约束。首版建议用维护窗口停写，台账保存断点。能否在可接受的窗口内完成，以副本实测为准。 |

**评审建议。** 保留平台管理员与项目负责人的分工。两个项目可以引用同一个资产标识，各自保存观察结果。原始证据单独授权。历史数据采用“有明确归属的迁入，有争议的受限待认领”。这样可以让项目 A 和 B 都处理同一个域名，同时保护彼此的截图、凭据、漏洞和统计。

## 二、项目模型和数据边界

### 模型和约束

| 对象 | 首版设计 | 约束与生命周期 |
| --- | --- | --- |
| 企业实例与资产归属企业 | 部署实例代表运营组织。`companies` 与 `company_scope` 继续描述资产归属和业务范围。项目可关联多个企业，同一企业可关联多个项目 | 平台维护企业目录，项目成员只见本项目引用的必要信息。企业名、域名命中、部门名和任务分类都不产生项目成员资格。 |
| 用户与成员 | `users` 保存内部 ID、状态和外部身份。`project_members` 记录项目、用户、角色、授权人、有效期与撤销时间 | 每人每项目同时至多一个有效角色。平台角色独立。项目可以有多位负责人，移除或降级最后一位有效负责人时须在同一事务完成移交。身份源强制停用优先，若因此产生无负责人的项目，由平台审计留痕后重新任命。 |
| 项目 | `projects` 保存稳定 ID、企业内唯一项目编号、名称、状态和创建人。普通项目有“进行中／已归档”两态，另有专用受限的历史待认领区 | 归档后保留成员读取与审计，停止业务写入、待发通知与服务账号访问。仍可撤权。恢复须登记原因，按当前成员与凭据重新核查。编号不回收，首版普通操作不支持项目间移动任务。 |
| 任务与业务对象 | 一个任务只属于一个项目。发现、复测、探索图、对话、工单材料和报告按其可验证父对象继承；独立会话、计划、项目文件及归档索引要有明确项目 | 保留原主键。有直接项目列和父对象的记录要保证两者一致。任务继承、发现归并、报告引用和导入均校验两端项目。新建与引用在同一事务检查，跨项目请求默认拒绝。 |
| 资产 | 内部共用最少的规范化标识，如资产类型与域名。引入项目资产记录，以项目与规范化标识唯一，给前端返回项目资产 ID。端口、技术栈、状态、凭据、首次/最近观察、来源和计数均按项目保存 | 全局去重仅用于内部存储。项目成员从自己的观察查询。相同标识在 A、B 中各有一条项目记录；A 新增端口或删除观察均不改变 B 的页面、统计或时间戳。 |
| 证据与附件 | 文件、快照、归档、报告版本有项目内的逻辑引用。正文可按哈希物理去重。下载走已授权的项目对象 | 哈希、路径或来源 URL 单独都不能换取正文。删除某一引用要考虑其他有效引用和留存要求。还原也须复核包内对象的归属。 |
| 服务账号与配置 | 一项集成在一个项目使用一个服务账号，令牌保留现有 scope、限额、有效期、吊销及来源约束。模型、通知渠道和技能定义由平台维护，按项目显式分配可用配置 | 生效范围取项目授权、令牌权限和原有限制的交集。首版机器接入默认仅开放获授权的脱敏读取。平台配置的密钥不进入项目响应，通知队列和投递记录携带项目。 |

**与当前实现的衔接。** 当前任务关联自己的探索图，来源任务有独立关联表。资产记录含多个任务 ID，域名和 IP 等有全局唯一索引，部分查询还会按来源任务或企业范围展开。首版要同时修改将来的数据写入方式与读取范围；仅给任务表增加项目列无法拆分既有混合观察。任务的 `share_global_assets` 在新模型内最多表示复用本项目已授权资产。[任务与资产结构](../db/schema.sql) · [资产上下文查询](../db/task_assets_context.go) · [任务上下文](../db/task_context.go)

**两个项目共用域名的示例。** A 项目留有某门户的截图和一条发现，B 项目只有同一域名的一次访问记录。两组都能在自己的项目看见这个域名。B 的发现计数为零，搜索、通知和导出也只包含 B 的记录。即便 A 和 B 共用一个物理正文，B 也须持有自己的、有来源的证据引用才能读取。一个同时参加两组的员工切换项目后，仍按所选项目的角色工作。

## 三、角色、敏感授权和执行位置

平台管理员负责身份源、平台配置、建项目、任命首位负责人及恢复管理。管理员在业务项目内的访问权来自实名项目成员关系。数据库和宿主机运维权限另行管控；应用角色只能约束经应用发起的访问。

下表是首版拟开放的业务权限。“单批”指单独申请、限定对象与期限，并由另一名有批准权的实名人员批准。“本人范围”指当前服务账号获准的资源和动作。

- **实名和撤权。** OIDC 首次登录只建立身份。平台管理员在受控初始化步骤绑定首个实名平台管理员，项目负责人显式添加成员。旧共享账号不映射为任何员工。所有请求检查用户与成员的当前状态。项目撤权提交后的新请求立即拒绝；长连接建议在 60 秒内断开，重连重新鉴权。企业身份源停用要有同步信号或定期核对，记录单独的传播时限。必要时由平台管理员在 ARTEX 本地立即停用。
- **数据分级。** 任务描述、报告正文、审计参数、模型消息和通知也可能含有原件内容。未经脱敏核验的旧文档按原件管理，只读成员仅见已发布摘要。附件预览、报告内嵌图和导出附件继承各自证据的敏感等级。可以编辑草稿或任务描述，不自动取得运行、工具放行、修改平台配置的权限，此类操作在独立授权设计通过前不向项目角色开放。
- **原件和签发。** 原件授权记录项目、对象、动作、用途、申请人、批准人和失效时间。默认单次导出、查看最多一个工作日；撤权或归档提前终止。项目负责人批准他人的原件申请；负责人本人申请时由另一位有效负责人批准。项目仅有一位负责人时，其本人走实名复核人独立批准路径。签发绑定不可变的报告版本和证据清单；作者即使改任复核人也不能签自己的版本。签发后普通只读成员只下载已审定的脱敏版本。
- **授权管理。** 平台管理员任免项目负责人；现任负责人维护其他成员、发起负责人移交。负责人不能批准自己的授权或角色变化，复核、临时访问及成员变动均记录实际双方身份。服务账号由项目负责人申请、平台管理员绑定，离开项目或凭据吊销即停止访问。历史操作者保留原始标识和“身份未知”，与新的迁移操作人分别记录。
- **授权判定。** 服务端先从可信父对象解析项目，再判断主体、成员角色、对象状态和敏感授权。跨项目或不可见对象统一按不存在处理，已可见对象的动作不足返回禁止。过滤发生在查询、聚合、分页和生成缓存之前。旧 URL、预览、文件直链、下载、MCP、SSE、看板计数和自动补全执行同一规则。项目未明确、映射冲突或检查失败时拒绝。
- **长任务与导出。** 后台事件携带项目、原始发起人和申请版本。入队、开始、发布结果、投递或领取下载分别复核授权。撤权后禁止新的数据交付并中止可取消的传输，已交付副本记录在审计中。暂未接入项目授权的旧全局工作区、原始流量浏览与后台入口对普通成员关闭。审计记录项目、主体、动作、对象/版本、结果、时间和关联事件 ID；审计页面和导出摘要本身也须脱敏。
- **数据库防护。** 相互引用的项目对象优先采用项目键与资源键组成的外键。应用查询统一使用项目条件，SQLite 与文件访问经同一授权服务。若补充 PostgreSQL 行级安全，运行账号与建表账号分开，验证表所有者和连接池的行为。RLS 对 SQLite 和本地文件没有覆盖。[PostgreSQL 16 行级安全](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)

现状中，网页 JWT 主体固定，MCP 令牌已经有独立审计与限权，SSE 按任务订阅，共享工作区存在按路径读写与预览的入口。这四条路径应列入首批兼容性测试。[网页登录](../server/auth.go) · [MCP 令牌](../db/api_tokens.go) · [事件订阅](../server/broadcast.go) · [工作区](../server/workspace.go)

### 企业单点登录（SSO）

**首版建议。** 一套私有部署接入一个企业身份提供方（IdP），以 OpenID Connect（OIDC）授权码流程和 PKCE S256 登录，由 Go 后端完成换码。员工沿用企业账号和企业 MFA 策略；ARTEX 单独维护项目成员、业务角色和敏感数据授权。仅提供 SAML 或 LDAP 的环境，可以通过已有企业身份网关转换为 OIDC；需要原生适配时单独评估。实际身份源、目录停用接口和网络可达性均待企业确认。[OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html) · [OAuth 2.0 安全实践](https://www.rfc-editor.org/rfc/rfc9700.html)

**一次员工登录的路径**

1. 用户从被分享的项目链接进入，页面提供“使用企业账号登录”。Go 服务建立短时、一次性的登录事务，记录与浏览器绑定的 state、nonce、PKCE 校验值及站内返回路径。回调使用预先登记的固定 HTTPS 地址，外部身份源及代理配置只能由平台维护。
2. IdP 完成认证，后端校验事务并换码，核验签名、允许的算法、issuer、audience、适用时的 azp、有效期与 nonce。只向预配置的 issuer 获取元数据和签名公钥；未知密钥可受控刷新，验证仍失败时拒绝登录。重复或过期回调不能建立第二个会话。客户端密钥从部署的密钥设施读取，登录记录仅保留结果和关联编号。[ID Token 校验](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)
3. 以唯一键 `(iss, sub)` 查找或创建内部用户，首次登录默认无项目，显示“已登录，等待项目负责人添加”。企业目录限制本应用可登录的人群，ARTEX 检查本地账号状态。同一员工改邮箱延用原 ID，同邮箱但主体不同则作为独立待授权身份。切换 issuer 或客户端导致主体变化时，由管理员根据独立的企业身份凭证复核绑定、保留前后标识并撤销旧会话。平台管理员的首次绑定由持有部署权限的运维人员预置确切主体，再由该人完成 SSO 验证，禁止以首个登录者认领管理员。
4. 后端签发随机本地会话，并由 `/api/auth/me` 返回展示身份和可见项目。用户回到原链接时重新检查项目权限。进入自己能访问的项目才返回业务数据。浏览器只持有服务端设置的同源 `__Host-` 会话 Cookie，设置 Secure、HttpOnly、SameSite=Lax 和 Path=/。状态变更请求另验 CSRF 与请求来源。SSE、预览、下载沿用同源会话；避免把会话令牌放入 URL、localStorage 或前端日志。企业版使用显式允许的同源入口和 CORS 策略。

**最小持久化数据。** 身份绑定保存内部用户 ID、issuer、subject、状态和最近登录时间；显示名及邮箱可更新。服务端会话保存随机标识的摘要、用户 ID、创建和最近活动时间、绝对到期时间、撤销时间及可选 IdP 会话标识 sid。登录事务短期保存，回调消费时原子失效。首版仅读取必要身份声明；后续调用企业目录使用独立、最小授权的连接凭据。建议初始策略为空闲 30 分钟、最长 8 小时，SSE 心跳不自动延长空闲期，实际时长由企业确认。成员角色在服务端按当前授权判定。

| 事件 | 服务端行为和验收标准 |
| --- | --- |
| 员工退出、切换账号 | 先撤销本地会话并清 Cookie，清理用户相关缓存和浏览器持久化的业务数据，再按 IdP 能力提供“同时退出企业账号”。企业登出失败时本地退出仍已生效。共用浏览器换人后，上一位用户的 Repeater 工作区、报告与事件不应重现。[OIDC RP 发起登出](https://openid.net/specs/openid-connect-rpinitiated-1_0.html) |
| 撤项目成员、停用员工 | 撤项目成员只影响相应项目；本地停用员工撤销其全部人员会话。新请求立即检查，已开事件流建议 60 秒内断开。离职发现依赖 IdP 停用通知或权威目录对账；建议具备该能力的部署以 5 分钟为传播目标，记录“目录变更、ARTEX 收到、本地生效”三个时间。无自动停用信号时由管理员本地停用并演练，单靠 OIDC 登录无法承诺 5 分钟。 |
| 企业统一登出 | IdP 支持后台登出时，校验签名、签发方、受众、事件声明、时间与防重放标识，再按 issuer 与 sid 或 sub 撤销匹配会话。保留人员身份和成员关系，允许仍在职员工重新登录。后台登出与目录停用分别验收。[OIDC 后台登出](https://openid.net/specs/openid-connect-backchannel-1_0.html) |
| IdP 不可用或目录同步中断 | 新登录返回可重试提示，告警记录故障开始时间。既有会话仍受本地停用、空闲与绝对期限约束；目录超过约定的新鲜度时暂停新授高权、原件读取与导出，恢复同步后再开放。应急管理仅限指定运维人员在受限管理通道短时修复身份源、撤会话或重新绑定管理员，每次记录操作者及原因，不恢复旧共享网页登录。 |
| 企业 MFA 与敏感操作 | 由企业 IdP 对 ARTEX 应用启用 MFA。若企业要求原件导出或管理身份源前再次认证，需与 IdP 约定可验证的认证强度与最近认证时间；拿不到相应证明时不得将操作记为已完成强化认证。项目的独立批准仍须单独核查。 |

**现有入口与切换。** 当前前端把同一 JWT 写入 localStorage 和可由脚本读取的 Cookie，SSE URL 也会附带 token；前端身份展示有固定用户 ID 与角色。切换前须盘点旧登录、初始化、改密、重置脚本、Basic Auth、SSE 和静态页面路由。企业 SSO 生效后仅显式开放登录起点、回调等必要认证入口，业务授权由 Go 服务执行；旧 JWT 的签发与接受同时关闭，清理旧浏览器凭据、缓存和用户数据。Basic Auth 如保留，仅用于部署入口访问控制，并保障回调可达。外部 `/mcp` 继续走项目服务账号令牌。回退演练须证明离职账号、旧 JWT 和已撤销令牌均不能重新取得业务数据。[当前登录后端](../server/auth.go) · [请求路由](../server/server.go) · [前端会话](../web/src/lib/auth.ts) · [SSE 连接](../web/src/lib/api.ts) · [浏览器工作区缓存](../web/src/components/repeater/repeater-store.ts)

**试点签收。** 用两个项目和三个身份（在职双项目成员、首次登录无项目成员、已停用成员），在同一浏览器完成登录、换人、退出与撤权。另测错误 issuer/受众、过期及重复回调、签名密钥轮换、同邮箱不同主体、IdP 故障与恢复、失去最后一个管理员后的受控恢复。记录实际传播时间、应急审计和剩余兼容性问题。试点前由企业身份管理员确认 IdP 产品与协议、MFA 要求、离职信号来源、会话期限及应急责任人。

## 四、老数据归属和认领规则

迁移前由业务负责人提供**任务 ID → 项目编号**的确认清单，记录依据、提交人、复核人和版本。企业名、分类、标题、目录名、主机名和历史操作者显示名只能产生候选项。无确认映射、出现多个归属或关联链不完整的对象进入历史待认领区。普通成员无法列出该区或从计数推断其中记录；指定的迁移经办人可看最少元数据，敏感原文另行审批。

| 存量对象 | 能确定归属时 | 歧义与异常 |
| --- | --- | --- |
| 任务、探索图、活动、关联来源任务 | 用确认清单映射任务。沿任务实际的 exploration_id 关联图与活动；软删除和归档任务保留原状态与 ID | 跨项目来源、父子关系暂停生效。保存历史边与理由到受限台账，不向另一项目呈现历史摘要。 |
| 资产、范围、锚点、任务情报 | 按任务关联建立项目资产。由能定位到任务的观察重建项目属性。凭据类情报按原件处理 | 对多个任务汇总过的资产旧行，只分配可证明的标识与事实；混合字段保留唯一受限副本。孤立资产、无来源全局同步结果待认领。 |
| 漏洞、归并组、报告、复测、对话 | 按任务或可验证的报告/复测外键归属。一个版本的全部正文、截图与成员须属于同一项目 | 空 task_id、被多个项目引用的对话、混合报告或孤立截图先隔离。派生的脱敏副本有独立 ID 并保留来源。缺失的复测或原件记缺口。 |
| 流量、快照、文件、会话记录 | 用发现与快照绑定、任务或会话引用建立项目对象。保留原哈希，在原有证据链上校验。文件转换为经授权可取的附件 | 同主机、同哈希、同文件名不能证明项目归属。全局流量和共享目录中无可核对关联的内容留在受限区。多项目引用同一物理原件，逐一复核各项目的原始来源。 |
| 历史任务归档 | 将归档索引绑定到所属任务，记录原包 SHA-256。按每种现存格式在隔离副本试恢复 | 包内可能含来源任务、共享主机历史或文件。未经逐项确认的旧归档只保留受限原包；项目成员只能获得已审核的项目版内容。恢复先暂存、再按当前权限入库，不自动激活旧分享或作业。 |
| 平台配置、令牌、定时任务、通知、日志与用量 | 平台保管配置。明确归属的项目在复核后重新绑定计划、渠道和服务账号。历史审计保留原 token ID；隔离环境中的敏感日志和完整模型记录仅按证据处理 | 旧 JWT 在切换时统一失效，旧 MCP 令牌保留历史并吊销，按项目重发。无项目或已删除任务留下的日志、台账和用量计入受限历史汇总。待发通知、重试与计划暂停到负责人确认接收端。 |

**认领流程。** 迁移经办人提交对象清单、目标项目、来源证明及关联对象预览，目标项目负责人确认，二者须为不同实名人员。复核通过后，在同一事务登记项目引用与审计；文件先暂存校验，再发布引用。两人意见不一致则保留待认领。批量认领复用相同流程。留存期和清理需要另行批准。遇到错配先撤销可见性、下载与未发投递，再按台账修正，追查已经导出的版本。

**认领示例。** 假设历史任务 101 已确认为 A、205 已确认为 B，二者指向同一全局资产。A 的发现有截图引用，B 的任务仅证明见过该域名，旧资产行另有来源不明的凭据。迁移结果是两条项目资产记录，一条仅属于 A 的发现与截图引用，以及一项受限待核对的旧记录；凭据不出现在任何项目视图。本例数字用于说明规则。

现有快照把头信息与正文哈希放在 PostgreSQL，正文、流量 SQLite、会话文件及压缩归档分布在磁盘。归档代码支持 v1 至 v4。当前版本说明指出复测历史尚未进入报告导出及任务归档，所以数据库中的复测记录需要独立核对。[证据设计](./漏洞流量证据.md) · [归档格式](../db/task_archives.go) · [归档文件](../server/task_archive_package.go) · [复测说明](../README.md#手动漏洞复测)

## 五、实施顺序、核对和回退

1. **只读盘点。** 在脱敏副本统计各对象数、跨任务资产数、孤立引用、空归属、归档版本、文件/快照哈希、旧令牌和待执行业务。记录预计批次数、临时空间、备份容量、停止写入时长与恢复耗时。归属台账含源对象、确认映射版本、处理结果、目标 ID 或引用、原因以及校验摘要。
2. **建立可还原的基线。** 切换窗口停止用户写入和所有后台写入者，包括事件投递、归档、流量录制与清理。收敛在途事务和文件暂存日志。取得一致时间点的 PostgreSQL、SQLite（含其一致性状态）、正文、工作区、归档、配置和密钥副本。实际核对密钥位置；当前 JWT 密钥可位于程序基目录。记录程序版本和恢复环境。先用离线副本验证可恢复，再进入正式回填。[密钥位置](../server/auth.go) · [启动与挂载](../docker-compose.yml)
3. **扩展与回填。** 由一次有版本的迁移任务持有迁移锁。现有启动流程会执行 schema 和种子数据，大批量归属转换独立于正常启动。先建项目、身份与台账，再迁任务根对象、子对象、文件引用，最后处理归档和集成。按稳定主键分批，用“迁移版本＋源类型＋源 ID＋目标项目／引用”做幂等键，提交批次时同时写检查点。崩溃后按检查点核验、续跑。文件先写临时区并校验，引用提交后才可见；重复运行保留同一组结果。[数据库初始化](../db/db.go)
4. **核对与切换。** 对每类源对象验证“源总数＝处理完成的唯一源对象数＋受限待认领数＋记录并批准的例外数”，三个集合互斥。有部分属性已提取、原行仍混合的，源对象只计入待认领，已提取属性另记派生引用。逻辑引用展开另算，核对两个项目引用一个标识时的基数；原件按字节数、哈希和引用链抽查，报告及归档清单逐份对账。外键和同项目约束验证通过后收紧字段。先用具名试点账号只读验收，再开放新系统写入。切换时阻断旧入口与凭据，仅恢复已确认的后台计划。
5. **回退分界。** 新系统尚未接受业务写入时，可隔离新实例并恢复完整的一致基线；旧版恢复只在原有受限访问范围内进行。若已开放写入，先停写、保全新变更及审计，对象级核对增量。优先向前修复；如必须降级，由业务负责人确认可接受损失或受控回放方案，再恢复成套备份并复核权限。撤销过的令牌、成员和积压外发任务不得因恢复旧快照而重新对外生效。

**停止切换的条件。** 出现跨项目可见、证据哈希不一致、未说明的计数差异、重复执行导致额外记录、恢复缺少关键文件或旧凭据仍能取得业务数据时，保持隔离并修正。已登记且确认封存在待认领区的历史歧义允许存在。停机窗口和备份保留期由副本演练与运维容量决定。

## 六、首版评审与验收

| 用例 | 预期结果 |
| --- | --- |
| 同一员工在 A 为分析员、在 B 为只读；另有只加入 A 的员工 | 前者仅能在 A 编辑。后者在列表、搜索、自动补全、总数、旧链接、事件流、文件与 MCP 中均看不到 B。 |
| 两项目报告引用相同资产名称或正文哈希 | 各自只看自己的观察与报告。删除 A 的引用后 B 仍可按自己的授权读取。 |
| 平台管理员未入项目；分析员改任复核人；负责人申请原件 | 管理员只能管平台。原作者无法签发自己编辑过的版本。本人无法批准自己的原件申请。审计员读到事件元数据，不能由事件跳转读取原件。 |
| 成员撤权时仍打开事件流、有导出任务或旧下载链接 | 新请求被拒，流在约定时限内断开，待生成或暂存的导出无法领取。项目凭据撤销后机器访问同时失效。 |
| 存量含共享资产、无任务发现、跨项目来源、混合归档和无归属流量 | 可证明对象进入指定项目，混合或孤立内容可在受限台账查到；项目成员无法通过还原、统计或导出取得它们。 |
| 批次中断、文件暂存后中断、整批重跑、前后两个时间点回退演练 | 旧 ID、证据哈希和引用数一致。新增业务有单独保全记录，回退后保留撤权效果。每种实际存在的归档版本都有试恢复结果。 |

**请评审的三个决定**

1. **项目组维护方式。** 建议首版直接维护实名成员，每人每项目一个角色。有整部门高频进出项目的需求时，再设计目录群组同步及冲突规则。
2. **敏感访问与复核分工。** 建议原件查看与导出单独审批，项目负责人不默认取得原件；报告由独立复核人签发。小团队至少预留两名能承担相应职责的人员。
3. **历史认领与切换窗口。** 建议按经确认的任务清单迁移，其余封存待认领。先在副本实测停写窗口；若业务承受不了实测时长，再评估增量同步的成本。

上述三个选择决定首版的数据结构、权限测试范围和迁移工期。首版认可的上线依据是两组成员隔离验收与历史数据对账结果。
